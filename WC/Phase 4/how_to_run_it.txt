How to run it

You need two terminals. In terminal B you stop and start the server while terminal A runs the load. The reporter prints t=..s, so you can time docker stop at about 30 s and docker start at about 60 s.

Start the cluster:

bash
docker compose up -d --build
docker compose ps        # servers should show (healthy)

Item 9: without fault tolerance (HEALTH_CHECK=off), repeat for each algorithm:

bash
# make sure all servers are up, then recreate the LB
docker start server1 server2 server3
HEALTH_CHECK=off LB_ALGORITHM=least_connections docker compose up -d --force-recreate load-balancer

# terminal A
docker compose exec -e CONFIG_LABEL=nofc_lc -e STOP_AT=30 -e START_AT=60 client python timeline_benchmark.py
# terminal B (at ~30 s, then ~60 s)
docker stop server2
docker start server2

Repeat with LB_ALGORITHM=least_response_time and CONFIG_LABEL=nofc_lrt. Expect ConnectionError/EOFError failures during the outage. Least connections should hit the dead server the most, because a dead backend always has 0 active connections. Least response time sends it traffic according to its stale EWMA.

Items 10 and 11: with fault tolerance (HEALTH_CHECK=on, the default):

bash
docker start server1 server2 server3
LB_ALGORITHM=least_connections docker compose up -d --force-recreate load-balancer
docker compose exec -e CONFIG_LABEL=ft_lc -e STOP_AT=30 -e START_AT=60 client python timeline_benchmark.py
# terminal B: docker stop server2   (~30 s)   then   docker start server2   (~60 s)

LB_ALGORITHM=least_response_time docker compose up -d --force-recreate load-balancer
docker compose exec -e CONFIG_LABEL=ft_lrt -e STOP_AT=30 -e START_AT=60 client python timeline_benchmark.py

Evidence for the report:

bash
docker ps --format "table {{.Names}}\t{{.Status}}"    # server2: Exited, then (healthy) after restart
docker compose logs load-balancer | grep HEALTH      # DOWN / UP events with timestamps order
docker compose logs load-balancer | grep LB-STATS    # per-backend counters and UP/DOWN

Each run produces results/phase4/<label>/timeline.png and timeline.csv. In the ft_* runs you should see:

the stopped server’s line drops to 0 while the other two roughly share the load (about 50 each at 100 req/s)
almost no failed requests, only any that were in flight on the server at the moment it stopped
the server’s line returning to a fair share a few seconds after docker start
